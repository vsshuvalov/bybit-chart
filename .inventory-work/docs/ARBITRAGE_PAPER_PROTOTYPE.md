# Venue-neutral arbitrage paper prototype

Этот прототип проверяет межбиржевой spot-арбитраж на публичных стаканах без
API-ключей и без возможности отправить реальный ордер. Bybit, Binance, OKX и
Bitget подключаются как равноправные источники; движок проверяет каждое
направление `buy venue -> sell venue`.

По умолчанию используется `symbol=AUTO`. Один публичный all-tickers запрос на
каждую площадку даёт лучший bid/ask, объём, оборот и изменение цены за 24 часа.
Из общих минимум для двух бирж USDT-пар сначала выбирается пул 150 рынков с
наибольшей консервативной ликвидностью. Площадка участвует в паре, только если
её 24h USDT-оборот не меньше 5 000 000; оценка пары равна минимуму среди
прошедших площадок. Поэтому один тонкий листинг не исключает рынок, ликвидный
на двух других биржах. Затем до 50 пар ранжируются по медианной абсолютной
24h-динамике. Так волатильность повышает приоритет только после фильтра
ликвидности.

## Динамический PAPER-инвентарь

В стандартном AUTO-режиме каждая площадка начинает с **500 USDT** и без
заранее созданного набора токенов. Все 50 пар остаются наблюдаемыми, а правила
размещения капитала задаются в панели или API. Значения по умолчанию сохраняют
исходный консервативный профиль:

- один сигнал не активирует токен;
- `activation_observations=5`: требуется 5 уникальных пар BBO-снимков с
  положительным net edge;
- `evidence_window_minutes=60`: сигналы должны попасть в скользящее окно 60
  минут; это же окно задаёт срок выхода при отсутствии новых сигналов;
- `max_active_symbols=2`: одновременно удерживается не больше двух токенов;
- `allocation_per_symbol_venue_usdt=50`: полный бюджет покупки одного токена
  на одной площадке вместе с модельной taker-комиссией;
- `notional=25`: верхняя граница одной арбитражной PAPER-сделки;
- активация требует, чтобы лучшие ask и bid каждый содержали минимум 20
  размеров настроенной предельной сделки;
- если подтверждённых сигналов нет в течение настроенного окна, остаток
  токена продаётся обратно
  в USDT по доступному BBO. При недостаточной глубине слот остаётся в состоянии
  pending liquidation, а новый токен не занимает его.

Поля можно менять перед отдельным сканом или запуском монитора. Для AUTO сервер
проверяет единый бюджетный инвариант:

```text
max_active_symbols × allocation_per_symbol_venue_usdt + notional <= 500
allocation_per_symbol_venue_usdt >= notional
```

Так на каждой бирже остаётся капитал как минимум для одной сделки заявленного
размера. Допустимые границы: сделка и аллокация от 10 USDT, 1–50 активных
токенов (но не больше размера universe), 1–100 сигналов и окно 1–1440 минут.
Снижение максимального числа активов переводит лишние, более новые позиции в
`pending_liquidation`; новый размер аллокации применяется только к следующим
активациям. Во время работающего монитора поля блокируются: чтобы применить
новый профиль, нужно остановить монитор, изменить значения и запустить его
снова.

Активационная покупка и ликвидация также списывают модельную комиссию и меняют
виртуальные балансы: токены не создаются бесплатным `deposit`. Эта политика
проверяет идею управления малым капиталом, но ещё не является реальным
исполнителем или гарантией сохранения исходных 500 USDT.
Метрика `strategy_pnl_usdt` оценивает весь портфель по bid за вычетом модельной
комиссии выхода и потому включает спред/комиссии активации и ликвидации. Если
для ненулевого актива нет свежего bid, метрика временно равна `null`, а не
показывает фиктивный убыток; `arbitrage_realized_pnl` остаётся отдельным
результатом только исполненных арбитражных маршрутов.

## Граница безопасности

- Используются только публичные market-data endpoints.
- В адаптерах отсутствуют методы создания, изменения и отмены ордеров.
- Все балансы и исполнения виртуальные.
- Комиссии задаются как предположения. Перед реальной торговлей их нужно
  заменить ставками конкретных аккаунтов.
- Шаги количества для BTC/ETH/SOL и минимум 10 USDT заданы консервативными
  статическими предположениями. Перед testnet их нужно получать из актуальных
  instrument-info endpoints каждой площадки.
- В AUTO используются лучшие bid/ask и их заявленный объём из all-tickers,
  а не полный L2-стакан. Minimum notional равен 10 USDT, но реальные lot step
  и instrument filters ещё не загружаются — это ограничение PAPER-этапа.
- AUTO не закупает весь список из 50 пар. Виртуальный инвентарь создаётся
  только после подтверждения сигнала и ограничен двумя токенами.
- Совпавшие цены в REST-снимках не гарантируют реального одновременного
  исполнения. Следующая стадия после подтверждения сигнала — WebSocket shadow
  mode, а не немедленное подключение денег.
- В all-tickers нет общего sequence number. PAPER-защита считает одинаковый
  BBO одним снимком в пределах минутного окна: это не позволяет повторять одну
  сделку на каждом poll, но разрешает заново возникший маршрут позднее.
- REST-снимки старше 5 секунд и пары снимков с временным расхождением больше
  2 секунд исключаются. Это всё ещё приближение, а не доказательство
  исполнимости с низкой задержкой.

## Запуск

Из корня проекта:

```bash
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m packages.api.app
```

Открыть `http://127.0.0.1:8000`. Dashboard и API обслуживаются одним
процессом; API-схема доступна на `http://127.0.0.1:8000/docs`.

Один цикл можно запустить напрямую:

```bash
curl -X POST http://127.0.0.1:8000/api/v1/arbitrage/scan \
  -H 'Content-Type: application/json' \
  -d '{"symbol":"AUTO","max_symbols":50,"notional":"40","activation_observations":3,"evidence_window_minutes":30,"max_active_symbols":3,"allocation_per_symbol_venue_usdt":"60","min_net_edge_bps":"5","risk_buffer_bps":"2","auto_execute":false}'
```

Непрерывное наблюдение:

```bash
curl -X POST http://127.0.0.1:8000/api/v1/arbitrage/start \
  -H 'Content-Type: application/json' \
  -d '{"symbol":"AUTO","max_symbols":50,"notional":"40","activation_observations":3,"evidence_window_minutes":30,"max_active_symbols":3,"allocation_per_symbol_venue_usdt":"60","min_net_edge_bps":"5","risk_buffer_bps":"2","interval_ms":2000,"auto_execute":true}'
```

Остановить монитор:

```bash
curl -X POST http://127.0.0.1:8000/api/v1/arbitrage/stop
```

## Что именно считается

Для заданного notional движок проходит по глубине ask-стакана покупателя и
bid-стакана продавца. Он использует исполнимую VWAP, а не last price:

```text
net PnL = sell proceeds - buy cost - buy fee - sell fee - risk buffer
```

Возможность отклоняется, если:

- один из стаканов устарел;
- временные метки двух площадок слишком сильно расходятся;
- объём меньше минимального notional или не кратен общему paper-шагу;
- та же пара снимков уже была виртуально исполнена;
- на глубине нет нужного объёма;
- на бирже покупки недостаточно виртуального USDT;
- на бирже продажи недостаточно виртуального базового актива;
- чистый edge ниже порога.

При paper-исполнении обе ноги применяются к виртуальному портфелю атомарно:
либо изменяются оба баланса, либо ни один.

## Критерий успеха теории

Отдельный положительный снимок ничего не доказывает. Минимальный shadow-период
— несколько недель с разными режимами рынка. Перед переходом дальше полезно
зафиксировать:

1. Положительный совокупный PnL после taker-комиссий и консервативного буфера.
2. Достаточное число независимых возможностей, а не один выброс данных.
3. Устойчивость результата при увеличении комиссии, задержки и slippage.
4. Приемлемую концентрацию инвентаря по биржам и стоимость ребалансировки.
5. Низкую долю stale/error/partial сценариев.
6. Положительный результат отдельно по каждой паре бирж, символу и рыночному
   режиму.

Даже при выполнении этих условий следующий безопасный шаг — testnet или
shadow execution с приватными read-only данными. Реальные торговые разрешения
и небольшой капитал добавляются отдельным компонентом после независимого risk
review.
